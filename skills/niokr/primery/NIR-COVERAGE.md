## 1.А Концептуальная модель: два подхода к контролю полиномиальной сложности

### 1.А.1 Геометрическая интуиция

Турингу-полный язык `L` (Python, Java, Go) можно представить как
**N-мерный политоп** `Π_L`, где каждая ось — это формализуемое
нарушение методологии Сигма (M1, M2, M3, M4, T, P5–P9, J1–J5 — на v0.4
имеется 22 такие оси). Произвольная программа `P ∈ L` — это **точка**
в этом политопе. Из каждой грани `Π_L` исходит вектор, длина которого
`‖v_i‖` соответствует степени нарушения программой `P` правила `i`:

- `‖v_T‖` — глубина рекурсии без `lru_cache` или итеративного
  переписывания;
- `‖v_M1‖` — наличие `while True` без `break` (бесконтрольная
  итерация);
- `‖v_P9‖` — частота `.all()` без `.limit()` в ORM-цепочках;
- … и аналогично для остальных правил.

**Класс полиномиально-вычислимых функций (FP)** — это **выпуклый
внутренний политоп `Π_FP ⊂ Π_L`**, заданный пересечением полупространств
`‖v_i‖ ≤ c_i`, где `c_i` — пороговое значение, гарантирующее
полиномиальность по теоремам [IEEE 2024](https://ieeexplore.ieee.org/document/10758446)
и [Mathematics 2024 Q1](https://doi.org/10.3390/math12213429).

### 1.А.2 Подход 1 — DSL-профиль (как в статьях, черновик аналитика)

> Заранее построить грамматику языка, политоп которого **совпадает**
> с `Π_FP` by construction.

Геометрически — **посадить специально выведенное растение** на
ограниченной грядке. Программист физически не может выйти за границы
`Π_FP`, потому что синтаксические правила DSL не позволяют. Псевдо-EBNF
из черновика аналитика (см. Приложение А) — попытка такой грамматики.

**Сильные стороны:** математически чистый подход, нулевая
ongoing-стоимость аудита, гарантия принадлежности к FP **by
construction**.

**Слабые стороны:** требуется **переписывание всего стека** — нельзя
смешивать с обычным Python/Java/Go. Operationally неприменимо к
существующему production-коду; ни одна крупная команда не
согласится на разработку только в DSL-подмножестве.

### 1.А.3 Подход 2 — наш: методологический аудитор (sigma-audit)

> Оставить язык `L` неизменным. Статически **обрезать** каждый
> торчащий вектор до `‖v_i‖ ≤ c_i` через систему детекторов и
> авто-фиксов с верификацией эквивалентности.

Геометрически — **стричь обычный куст в форму вписанного 22-гранника**.
Каждый из 22 детекторов v0.4 — это **режущая плоскость**, перпендикулярная
одной из осей нарушения; программа считается находящейся в `Π_FP`,
когда **все 22 плоскости** проходят между ней и соответствующими
гранями `Π_L`.

| Геометрический объект | Реализация в `sigma-audit` v0.4 |
|---|---|
| Режущая плоскость по оси `v_i` | один детектор (например, `naive_recursion_no_memo`, `await_in_loop`, `unbounded_orm_all`) |
| Сила реза (auto-fix) | трансформер с `verify` (12 из 22 детекторов имеют пару) |
| Реальное измерение длины вектора | `count(violations[rule_i])` → density-метрика |
| Программа `P` лежит в `Π_FP` | `sigma-audit audit --gate strict` → exit 0 (PASS) |
| Программа выпала из `Π_FP` по оси `v_i` | violation registered with `rule_i` |
| Расстояние программы до `Π_FP` | агрегированная density (violations per file) |
| Sandbox-режим | пробная стрижка на копии куста перед тем как трогать оригинал |
| `--max-passes 5` | итеративная стрижка (chained patterns: J1 → P7) |

**Эмпирическая проверка модели — 5 контрольных корпусов** дают разные
точки в `Π_L`:

| Корпус | Density | Метафорически |
|---|---:|---|
| `yandex-cloud/python-sdk` | 0.000 | уже внутри `Π_FP` (все 22 вектора короче `c_i`) |
| `etna-team/etna` (Т-Банк) | 0.030 | у границы; 13/15 векторов обрезаются авто-фиксом |
| Yandex (7 repos) | 0.045 | в основном внутри, локальный «выступ» в одном тестовом фреймворке |
| MTS среднее | 0.144 | за границей по 1–2 осям (P8 await_in_loop = 75 %) |
| Python-master | 0.167 | за границей по T (рекурсия без memo = 49 %) |
| Сбер AI `giga_agent` | **0.806** | **сильно** выпала из `Π_FP` сразу по двум осям (P8 + P9) |

### 1.А.4 Гибридная стратегия (что отличает POLINOM от обоих чистых подходов)

Метафора подсвечивает **третью операционную возможность**, которой нет
ни у DSL-подхода, ни у чистого аудита:

> **Стрижка существующего куста** (`sigma-audit` CLI) **+ посадка
> новых веток сразу в форме** (`agent-rules` для AI-ассистентов).

- `sigma-audit audit/fix/sandbox` подрезает **существующий код** до
  формы `Π_FP` — машинная стрижка для 12 правил, ножницы под надзором
  архитектора для 10 detect-only.
- [`agent-rules/SIGMA-PYTHON.md`](../agent-rules/SIGMA-PYTHON.md) +
  планируемый `SIGMA-JAVA.md` дают LLM-агентам инструкции **писать
  новые ветви сразу в форме**, не выходя за `Π_FP`.

**Operationally сильнее DSL-подхода**: программист продолжает писать на
обычном Python/Java, но AI-ассистент молча следит, чтобы новые куски
не торчали за `Π_FP`; `sigma-audit` периодически подравнивает то, что
не уловил агент. У нас **два инструмента**: садовые ножницы (CLI) и
формы-направляющие (agent-rules pack).

### 1.А.5 Практические следствия для коммерческой коммуникации

1. **Density v/file = «насколько куст торчит»** — интуитивно понятная
   метрика для нетехнической аудитории (compliance-офицеры
   банков, эксперты ФСТЭК, продуктовые директора). Можно говорить
   «ваш код выпирает на 0.144 единицы в среднем» вместо «у вас 249
   нарушений правил M1–P9».

2. **Auto-fix vs detect-only** ⇔ **прямая стрижка vs ручная
   подрезка под наблюдением садовника**. 12 авто-трансформеров
   делают рез механически; 10 detect-only требуют решения архитектора.

3. **Возражение «у нас и так всё нормально» — парируется метафорой
   регрессионной защиты.** Корпус `yandex-cloud/python-sdk` (2 180
   файлов, 0 нарушений) — точная иллюстрация: куст уже подстрижен
   дисциплиной команды и code review. Pitch таким клиентам — **не**
   «найдём ваши проблемы», а **«регрессионная защита — ножницы,
   чтобы куст не вырос обратно**: при найме новых людей, при
   рефакторинге, при добавлении новых модулей форма не должна
   сломаться». Sigma-audit становится **CI-gate** на сохранение уже
   достигнутого стандарта, а не инструментом разовой расчистки.

4. **Концептуальный сдвиг относительно черновика аналитика**
   (см. [`docs/REVIEW-RESPONSE-PSAFE-DRAFT.md`](REVIEW-RESPONSE-PSAFE-DRAFT.md)):
   POLINOM — это **профиль аудита** существующего кода с
   auto-fix-конвергенцией к норме и measurable density-метрикой
   прогресса; **не** закрытый DSL для новой разработки. Геометрическая
   модель формально показывает, что обе позиции приводят к одному
   `Π_FP`, но **операционные траектории кардинально разные**.

## 2. Методология статьи: универсум формализуемых нарушений

В статье IEEE 2024 авторы формулируют **4 условия** на программу в §F
плюс **Теорему 2** о полиномиальной сложности. Эти условия операционализованы
в проекте POLINOM как **5 методологических идентификаторов**:

| ID | Источник в статье | Содержание |
|---|---|---|
| **M1** | §F.1 + §A.3 | Только `FOR` по конечному списку как итерационная конструкция |
| **M2** | §F.3 + §D | Контролируемая рекурсия (Gandy + уточнение Нечесова: структурный спуск + `\|f(a)\| ≤ \|a\|+c`) |
| **M3** | §F.4 | Определимые функции в порядке зависимостей (нет `def` в циклах, нет forward-refs) |
| **M4** | расширение POLINOM | Отсутствие mutable global state в рекурсии (наше расширение, согласованное с духом Gandy) |
| **T**  | §H, Theorem 2 | Следствие: код, проходящий M1-M3, гарантированно полиномиально вычислим |

Дополнительно, для Python-редакции методологии вводятся **операционные
правила P5-P9** (Python-специфичные оптимизации, не отменяющие M-rules) и
**5 анти-паттернов J1-J5** (Java-привычки, вредные в CPython).

### 2.1 Таксономия AST-форм нарушений

Эмпирически перечислены **~95 различных синтаксических форм**, в которых
может быть выражено нарушение M-rule, P-rule или J-rule:

| Правило | Кол-во форм | Примеры форм нарушений |
|---|---:|---|
| **M1** | ~10 | `while True` без `break`, `while cond` с не-убывающим cond, `itertools.cycle`, бесконечный generator, recursion-as-iteration, `for _ in itertools.count()`, unbounded `iter(callable, sentinel)`, threading event-loop |
| **M2** | ~12 | `f(xs[1:])`, `f(n-1)+f(n-2)`, mutual recursion, ackermann, slice-by-step `f(xs[2:])`, accumulator-recursion без descent, generator recursion, `yield from f(...)` без base-case, tree-walk без cache |
| **M3** | ~6 | `def` внутри `for`, `lambda` с capture loop var, redef в if/else, forward-ref, dynamic class с method-redef, `exec`-defined function |
| **M4** | ~5 | `global X` + рекурсия, `nonlocal X` mutation в рекурсии, рекурсия мутирует module-level list, рекурсия пишет в class attribute, mutation параметра outer scope |
| **T** | ~6 | unmemoised binary tree walk, branching scan без cache, partition без memo, coin-change без memo, edit-distance без memo, n-queens-style backtracking |
| **P5** | ~14 | manual `sum`, `max`, `min`, `any`, `all`, `count`, `filter+map`, manual `zip`, manual `enumerate`, manual `dict` build, manual `list` build, manual `set` build, manual `sorted`, manual substring search, build-list-then-len |
| **P6** | ~6 | dict mutation в `for k in d`, list mutation в `for x in xs`, set mutation, generator advanced inside its consumer, `dict.popitem` в цикле, list `.remove(x)` в `for` |
| **P7** | ~5 | `s += part` в цикле, `s = s + x`, `'%s%s' % (s, x)` в цикле, f-string concat в цикле, `bytes += chunk` в цикле |
| **P8** | ~7 | `await fn(x) for x in xs` (sequential), `async def` без `await`, `asyncio.create_task` discarded, blocking I/O в `async def`, `time.sleep` в async, `requests` в async, missing `async with` |
| **P9** | ~8 | N+1 query, `.all()` unbounded, missing `selectinload`/`joinedload`, commit-in-loop, `query.count()` после `.all()`, lazy-load в шаблоне, sync ORM в async, missing index hint |
| **J1** | ~3 | `for i in range(len(x))`, `for i in range(0, len(x))`, `enumerate` ignored when index needed elsewhere |
| **J2-J5** | ~8 | `if k not in d: d[k]=...`, `if len(x) > 0:`, `try/except: pass` swallow, manual getter/setter property, builder pattern, factory class for trivial init, type-coded enum, `is_empty()` метод когда `__bool__` достаточно |

**Всего: ~95 форм-классов**, из которых:
- *Ядерная методология* (M1-M4 + T) = ~39 форм;
- *Python-специфичные* (P5-P9) = ~40 форм;
- *Java-anti-patterns* (J1-J5) = ~16 форм.

#### v0.4 — критически важные дополнения по итогам MTS-дoгфуда

- **`manual_filter_loop`** — caught 4 production-кейсов в FastAPI-JSONAPI
  и onETL, успешно auto-fix'ятся в filtered list-comprehension.
- **`manual_set_build`** — симметричный к `manual_dict_build`; страховка
  на будущих корпусах (на MTS не сработал, но детектор готов).
- **`unbounded_orm_all`** — нашёл **14 P9.2-нарушений** в data-rentgen и
  syncmaster — потенциальные DoS / OOM-уязвимости. Высокая ценность
  для финансового аудита по 683-П.
- **`async_def_no_await`** с **Template-Method suppressor** — **81
  нарушение** на MTS (без suppressor было бы 141 — каждый
  framework-hook ложно срабатывал). Это самая крупная единичная
  находка v0.4.

### 3.2 Принцип «precision-over-recall»

Детекторы реализованы **узкими** — ловят каноническую AST-форму, а не
все семантически эквивалентные варианты. Это сознательный выбор:
- В режиме `auto-fix` ноль ложноположительных срабатываний — критично
  для безопасной массовой переписки кода через `sigma-audit fix`.
- Цена — пропуски: например, `manual_list_append` ловит
  `r=[]; for x: r.append(f(x))`, но не ловит
  `r=[]; for x: if cond: r.append(f(x))` (требуется conditional
  comprehension с `if`).

Для широкого recall'а пользователю рекомендуется параллельно использовать
универсальные линтеры (см. §6).

## 4. Покрытие — цифры

### 4.1 Теоретическое покрытие (по AST-формам)

Сумма частичных recall'ов по всем правилам, нормированная на 95 форм:

| Правило | Покрыто форм | Из всех | Recall | Что пропущено |
|---|---:|---:|---:|---|
| **M1** | ~1.5 | ~10 | **15%** | `itertools.cycle`, бесконечные generator'ы, recursion-as-iteration |
| **M2** | ~3 | ~12 | **25%** | mutual recursion, `f(xs[2:])`, accumulator, generator-recursion |
| **M3** | 0 | ~6 | **0%** | `def`/`lambda` в цикле — целая категория |
| **M4** | ~2.5 | ~5 | **50%** | `nonlocal`, mutation без `global` keyword, mutual recursion с globals |
| **T** | ~4 | ~6 | **65%** | `naive_recursion_no_memo` ловит double-recursion; редкие формы (n-queens) пропущены |
| **P5** | ~6 | ~14 | **42%** | manual `any`/`all`/`min`, manual `zip`/`enumerate`, manual `set` build |
| **P6** | ~3 | ~6 | **50%** | list mutation в своей итерации (близнец dict_mutation, не реализован) |
| **P7** | ~2 | ~5 | **40%** | `s = s + x`, `bytes += chunk`, f-string concat в цикле |
| **P8** | ~1.5 | ~7 | **20%** | `async def` без `await`, `time.sleep` в async, missing `async with` |
| **P9** | 0 | ~8 | **0%** | вся ORM-категория |
| **J1** | ~1.8 | ~3 | **60%** | хорошее покрытие |
| **J2-J5** | ~1 | ~8 | **12%** | `dict_init_if_missing` ловит только J4 |

**Итог:** **~28 из 95 форм ≈ 30%** теоретического покрытия.

### 4.2 Практическое покрытие (по частоте в реальном коде)

Распределение нарушений в реальных Python-проектах **не равномерное**.
По данным консолидированных PR-роллапов на open-source проектах
(numpy, pandas, scikit-learn — Ruff PERF/SIM/FURB applications) частота
встречаемости составляет:

| Форма нарушения | Доля от всех Sigma-нарушений | Покрыта в v0.3 |
|---|---:|:---:|
| `manual_list_append` | ~30% | ✓ |
| `manual_dict_build` | ~10% | ✓ |
| `if k not in d: d[k]=…` (J4) | ~8% | ✓ |
| `for i in range(len(x))` (J1) | ~5% | ✓ |
| `s += x` в цикле (P7) | ~3% | ✓ |
| `manual_sum`/`max`/`min` | ~7% | частично |

#### 4.4.1 Эмпирическое подтверждение chained anti-patterns

Главный научный результат этого замера — **впервые на боевом проекте
зафиксирован эффект цепочечных анти-паттернов**, обосновывающий
архитектурный выбор многопроходного фикса (`--max-passes`):

| Файл | До fix | После fix | Объяснение |
|---|---|---|---|
| `data_structures/arrays/permutations.py:11` | **J1** (`range_len_indexed`) | **P6** (`dict_mutation_in_iter`) | Трансформер `for i in range(len(nums))` → `for x in nums` обнажил мутацию `nums` в теле цикла — **уже-баг с `RuntimeError`**, ранее замаскированный индексным циклом |
| `cellular_automata/wa_tor.py:445` | (скрыто) | **P6** (`dict_mutation_in_iter`) | Аналогично — фикс внешнего паттерна сделал видимой мутацию в итерации |

Этот результат имеет **двойное значение**:

1. **Методологическое:** доказано, что некоторые нарушения методологии
   можно обнаружить только итеративно, после применения трансформации
   к outer-паттерну. Однопроходный детектор фундаментально не способен
   их найти. Подтверждена необходимость `detect → transform → re-detect`
   цикла, реализованного как `--max-passes N` (default 5).
2. **Practical safety:** инструмент находит **реальные runtime-баги**
   (RuntimeError при изменении dict в иттерации), которые ускользают
   от поверхностной проверки. На production-кодовой базе Сбербанка
   ожидается аналогичный эффект — фиксация одного класса нарушений
   обнажает другой.

**Эмпирический вывод:** разные домены порождают **разные топ-1
правила** (P8, T, M1, P5, J1 — все 5 групп представлены). Это
**ключевой аргумент в пользу полного покрытия M1–M4 + T + P5–P9 +
J1–J5**: специализированный «top-3 правил» подход бы
систематически упускал значительную часть нарушений. Подтверждает
архитектурный выбор v0.4 — широкое покрытие головы методологии,
а не глубокая специализация на одном правиле.

## 5. Сравнение с существующим инструментарием

### 5.1 Универсальные Python-линтеры

`sigma-audit` **не заменяет** общеотраслевые линтеры. Его роль —
*методологическая классификация* нарушений в терминах правил M/T/P/J.

| Инструмент | Кол-во правил | Что покрывает | Перекрытие с `sigma-audit` |
|---|---:|---|---|
| **Ruff** ([astral-sh/ruff](https://github.com/astral-sh/ruff)) | ~900 | PERF, SIM, FURB, B, ASYNC, C4, PIE и др. | Частичное по канонической head-форме (manual list-comprehension, J4 setdefault, range-len-indexed) |
| **Pylint** | ~400 | code-smell, complexity, design | Минимальное — другая категория проверок |
| **flake8-async** | ~15 | async-checkpoints, sync-call в trio | Минимальное; наш `await_in_loop` — отдельный угол |
| **refurb** | ~170 | modern idioms (`pathlib`, `setdefault` и др.) | Перекрывается с `dict_init_if_missing` (FURB173-style) |
| **perflint** (deprecated, влит в Ruff PERF) | ~5 | manual list-comprehension, list-cast, try-в-цикле | Прямое перекрытие с `manual_list_append`, `manual_dict_build` |

### 5.2 Уникальная ценность `sigma-audit`

В чём `sigma-audit` отличается от Ruff и аналогов:

1. **Привязка к научной методологии.** Каждое нарушение явно отнесено
   к правилу M-rule / T / P-rule / J-rule с цитатой источника
   (IEEE 2024). Ruff отвечает на вопрос «что переписать», `sigma-audit` —
   «какое правило методологии нарушено и почему».
2. **Sigma-score.** Агрегированный показатель по проекту с весами
   серьёзности (Error/Warning/Info) — для compliance-аудитов и НИОКР.
3. **Эмпирические multipliers в CTA.** На основе бенч-данных
   `sigma-bench` (Apple M2, CPython 3.13) выводится диапазон ожидаемого
   ускорения от каждого фикса (×0.5–1.5 для P1-инвертирующих, ×100–1000
   для T-нарушений).
4. **Ссылка на ГОСТ-19 документацию.** Полный комплект документов
   (ТЗ, ОП, ПМИ, РО, РС) — для официальной сдачи в составе НИОКР.
5. **`# sigma:allow` маркер.** Явное acknowledgment легитимных
   исключений (daemon-loops, rate-limited await) — не просто игнор,
   а ссылка на правило с reason'ом.

### 5.3 Рекомендованный stack

Для production Python-проекта:

```
ruff check + ruff format        # широкое покрытие best-practices
+ flake8-async                  # async-специфика
+ sigma-audit audit             # методологический аудит по Сигме
+ mypy                          # типы
+ pytest                        # корректность
```

Эти инструменты **дополняют** друг друга, не конкурируют.

## Приложение А — Псевдо-EBNF профиля P-Safe-Python

Настоящее приложение задаёт **формальную грамматику допустимого
подмножества** Python-программ относительно методологии Сигма
([Goncharov/Nechesov/Sviridenko, IEEE 2024](https://ieeexplore.ieee.org/document/10758446);
[Nechesov, Mathematics 2024 Q1](https://doi.org/10.3390/math12213429)).
Программы, синтаксически принадлежащие этому подмножеству и
проходящие статический анализ, сохраняют все доказанные в статьях
свойства полиномиальной вычислимости (FP-класс) и гарантированного
завершения.

EBNF приведён в инженерной нормализации; конкретные детекторы
`sigma-audit v0.4` (см. § 3.1) реализуют статическую проверку
принадлежности произвольной Python-программы этому подмножеству.

```ebnf
Program          ::= Definition*
Definition       ::= NonRecursiveDef | RecursiveGroup
NonRecursiveDef  ::= "def" Name Params "=" Expr
RecursiveGroup   ::= "recgroup" "{" RecursiveDef+ "}"
RecursiveDef     ::= "def" Name Params RecContract "=" Expr

RecContract      ::= "decreases" "(" Measure ")"
                   | "gandy_call_guard" "(" GuardSpec ")"

Expr             ::= IfExpr | ForExpr | CallExpr | ValueExpr | LetExpr
IfExpr           ::= "if" BoolExpr "then" Expr "else" Expr
ForExpr          ::= "for" Var "in" FiniteCollection "do" Expr
CallExpr         ::= Name "(" Args ")"
FiniteCollection ::= ListExpr | ArrayExpr | RangeExpr | InputDerivedCollection
```

### А.1 Соответствие EBNF-правил детекторам v0.4

Каждое EBNF-правило соответствует одному или нескольким
имплементированным детекторам, которые статически детектируют
**отклонения** Python-программы от данного подмножества:

| EBNF-правило | Норма | Детекторы, проверяющие нарушение |
|---|---|---|
| `IfExpr ::= "if" BoolExpr "then" Expr "else" Expr` | условные операторы — единственная разрешённая ветвящаяся конструкция | (нет нарушений на уровне `if/else` — Python-конструкция совпадает с нормой) |
| `ForExpr ::= "for" Var "in" FiniteCollection "do" Expr` | итерация только по конечным коллекциям | `J1 range_len_indexed` (запрет индексации через `range(len(xs))`); `M1 while_true_no_break` (запрет произвольных `while True`); `P7 dict_mutation_in_iter`, `P7 list_mutation_in_iter` (v0.5) (запрет мутаций коллекции в собственной итерации) |
| `RecursiveDef … RecContract` | рекурсия только под контрактом убывания | `T naive_recursion_no_memo` (требует `@lru_cache` или итеративное переписывание); `P2 linear_recursion` (контролирует структурный rank/length) |
| `RecursiveGroup ::= "recgroup" "{" RecursiveDef+ "}"` | взаимная рекурсия в конечной группе | (для v0.5+: проверка SCC call-graph и ограничение на количество функций в группе) |
| `NonRecursiveDef` (тело) | отсутствие определений функций внутри циклов | `M3 def_in_loop` (v0.5) — запрет `for x in xs: def f(...)` |
| `FiniteCollection` для `ForExpr` | размер коллекции должен быть полиномом от размера входа | `P9 unbounded_orm_all` (запрет `.all()` без `.limit()` — потенциально не-полиномиальный размер); `P5 manual_*` (нормативное приведение к comprehension с явной ограниченной коллекцией) |
| Запрет `eval`/`exec` (динамическая генерация кода) | программа задана последовательностью статических определений | (системный запрет; не имплементирован как детектор, потому что использование `eval`/`exec` в production Python-проектах редко) |

### А.2 Множество допустимых программ `K_Python`

Пусть `K_Python` — класс Python-программ, удовлетворяющих:
1. синтаксическим правилам EBNF выше;
2. семантическому контракту убывания на каждой рекурсивной ветви
   (формальное определение — статья IEEE 2024, § 4.2);
3. полиномиальной ограниченности размеров промежуточных коллекций
   (формальное определение — статья Mathematics 2024 Q1, FPAG-теорема).

**Программа `P` принадлежит классу `K_Python`** ⇔
`sigma-audit audit P --gate strict` возвращает `exit 0` (статус
**PASS**).

`sigma-audit fix --max-passes 5` строит **отображение** `f: P → P'`,
где для 12 из 22 текущих v0.4-детекторов `f` гарантированно сводит
программу с нарушением к программе из `K_Python` (или ближе к
`K_Python` — для chained-нарушений может потребоваться несколько
проходов). `verify` доказывает функциональную эквивалентность `P`
и `f(P)` на конечном множестве входных значений.

### А.3 Что EBNF **не покрывает** в v0.4

EBNF — формальная грамматика **синтаксической** структуры. Семантические
ограничения (полиномиальная длина результата, корректность контракта
убывания на конкретных значениях параметра) выходят за пределы
статического анализа без помощи аннотаций. В v0.5 планируется ввести
поддержку аннотаций вида:

```python
@p_recursive(decreases="len(xs)")
def f(xs: list[int]) -> int:
    if not xs:
        return 0
    return xs[0] + f(xs[1:])
```

Что соответствует Java-варианту `@PRecursive(decreases="list.size()")`
из черновика аналитика (см.
[`docs/REVIEW-RESPONSE-PSAFE-DRAFT.md`](REVIEW-RESPONSE-PSAFE-DRAFT.md) § 1.3).

### А.4 Расширение на Java и Go (roadmap)

EBNF выше — Python-конкретизация общего профиля P-Safe. По итогам
ревью черновика аналитика плановое распространение:

- **POLINOM-JAVA** (Phase 1 НИР со Сбером, 2026) — те же правила
  с заменой синтаксиса (`for-each`, аннотация
  `@PRecursive(decreases=...)`, запрет `while`, `do-while`,
  reflection-вызовов в pSafe-ядре).
- **POLINOM-GO** (v0.7+ roadmap) — `for ... range`, запрет
  `for {}`, контракт убывания через комментарии-аннотации либо
  через linter-расширение, точечные правила на goroutine-leak
  / channel-receive-loop.
