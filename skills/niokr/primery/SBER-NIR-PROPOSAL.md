# Инвестиционное предложение для ПАО Сбербанк

**Тема:** Содержательное наполнение НИР «ПОЛИНОМ» — методологический статический анализатор кода (Phase 1: Python production audit + Java baseline + ТЗ Java-CLI; Phase 2–3: Java-CLI v1.0 + интеграция в GigaCode и GitVerse)

**Кому:** Дирекция программы партнёрства с центрами ИИ второй волны / Блок технологий и данных, ПАО Сбербанк

**От кого:** Центр Искусственного Интеллекта НГУ совместно с Институтом математики им. С. Л. Соболева СО РАН

**Дата:** Май 2026

---

## Контекст

ПАО Сбербанк в 2026 году инвестирует около **350 млрд рублей** в генеративный ИИ и ожидает эффекта в **100 млрд рублей** в текущем году. Параллельно действует соглашение о партнёрстве с центрами ИИ университетов второй волны, в рамках которого Сбербанку и НГУ необходимо определить содержательное наполнение НИР первого этапа на сумму **25 000 000 рублей**.

### Где мы стоим в ландшафте инструментов качества кода

Существующий инструментальный стек разбит на **два уровня дороговизны**:

- **Уровень 1 — массовый SAST** (SonarQube, Coverity, Snyk, Solar appScreener, PT AI). От 0 до ~8 М ₽/год. Закрывает security-CWE и code smells. **Не различает** O(N²) от O(N) в горячем пути; не видит «эффективность алгоритмов» из ГОСТ Р 56939-2024 §5.10 как программную проверку. Регуляторно эту часть § закрывает **с оговоркой**.
- **Уровень 3 — формальные верификаторы** (Coq, F\*, Frama-C, Astrée, Polyspace, ИСП РАН). От 50 К $/seat/year или 50–200 М ₽ за многомесячный НИР-проект. Закрывает всё, но не масштабируется на production-кодовую базу банка из 500К LOC без переписывания.

Между ними — **ничья земля**: «допустимое время отклика» из ГОСТ Р 57580.4 §5, «гарантированное завершение» из Приказа ФСТЭК № 31, УБИ.034 (исчерпание ресурсов) из БДУ ФСТЭК. ФСТЭК и ЦБ это требуют. SAST это не закрывает. Formal verifier — закрывает за такие деньги и сроки, что массовый банковский Python не доходит.

ПОЛИНОМ — **третий уровень между**. Не дорогая команда математиков, не дешёвый SAST. Готовый production-инструмент с теоремой Кобэма за основой, который **программно закрывает ту часть требований ФСТЭК и ЦБ, которую SAST технически не видит, а formal verifier закрывает слишком дорого**. См. позиционирование — [`docs/VISION.md`](VISION.md).

ПОЛИНОМ не конкурент GigaCode и не альтернатива внутренним инструментам качества кода СберТеха. Это **дополняющий слой** к существующему стеку: SonarQube / Coverity — security-CWE; GigaCode — context-aware completion; ПОЛИНОМ — методологическая классификация нарушений с программно-доказуемой привязкой к нормативной базе РФ (CWE / БДУ / ГОСТ в каждом отчёте, см. [`docs/SIGMA-CWE-MAPPING.md`](SIGMA-CWE-MAPPING.md)).

Научной базой служит методология академиков С. С. Гончарова, А. А. Нечесова и Д. И. Свириденко (Институт математики им. С. Л. Соболева СО РАН), опубликованная в [IEEE SIBIRCON 2024](https://ieeexplore.ieee.org/document/10758446) и в журнале [Mathematics, 2024 Q1](https://doi.org/10.3390/math12213429). Методология формально устанавливает критерий принадлежности программ Тьюринг-полного языка к классу FP.

## Продукт

`sigma-audit` (ПОЛИНОМ) — production-готовый программный комплекс, состоящий из:

- **CLI-инструмент** (Python-пакет, `pip install sigma-audit`) — текущая версия v0.5.2 содержит **32 канонических детектора в 7 семействах** (M / T / P / J / S / R / X — см. ниже), **21 авто-трансформер с верификацией эквивалентности** через verify-протокол, режим `sandbox` (единый workflow `clone → audit → fix → audit → HTML-отчёт`) и **каскадный аудит до 5 слоёв** (раскрывает анти-паттерны, скрытые под другими паттернами).
- **Web-playground** (https://polinom-sigma-audit.up.railway.app) — публичный интерфейс с multi-user concurrency. Принимает три формы входа: GitHub-URL, публичная папка Я.Диска (для приватного кода — privacy-mode, payload не кэшируется), magic self-marker. Пользователь получает HTML / MD / SARIF отчёт за 30 секунд.
- **Agent-rules pack** для AI-агентов (Claude Code, Cursor, GitHub Copilot, универсальный) — 4 IDE × 3 языка (Python / Java / TypeScript). Применяет правила в момент написания кода, не post-hoc.
- **Полный комплект ГОСТ-19 документации** ред. 2.0 (5 документов: ТЗ, ОП, ПМИ, РО, РС, ИРМ).

| Семейство | Что закрывает | Регуляторная привязка |
|---|---|---|
| **M** (manual loops) | Ручные циклы вместо C-built-ins | CWE-407, 834 → ГОСТ 56939 §5.10 «эффективность алгоритмов» |
| **T** (template-method) | Naive recursion + manual sort | CWE-1334, 407 → УБИ.140 |
| **P** (poly recursion / async) | Линейная рекурсия, `await_in_loop`, `async_def_no_await`, ORM unbounded | CWE-674, 405, 1041 → УБИ.034, 043 → ГОСТ 57580.4 §5 «время отклика» + Приказ ФСТЭК № 31 |
| **J** (judgement) | Range-len iteration, dict-init-if-missing, while-True-no-break | CWE-1041, 835 |
| **S** (spatial / memory) | Recursion accumulator, tee unbounded, recursive collect, nested comp, `lru_cache` без maxsize, deepcopy в цикле | CWE-770, 400 → УБИ.034 |
| **R** (regex / ReDoS) | Catastrophic backtracking, `re.compile()` в цикле | CWE-1333, 1334 → УБИ.034 |
| **X** (XML / Billion Laughs) | Unsafe stdlib XML parsers | CWE-776, 611 → УБИ.157 |

Pytest 80 / 80 проходит. Tsc на frontend exit=0.

Продукт не заменяет SonarQube, Coverity, GigaCode AI Code Review, Bandit и аналогичные инструменты. Они образуют **дополняющий стек**: общеотраслевые анализаторы покрывают code smells и общие best-practices; GigaCode — context-aware completion и code review-комментарии; ПОЛИНОМ — методологическую классификацию нарушений с формальным обоснованием по теоремам IEEE 2024 и Mathematics 2024 Q1, и с автоматическим маппингом каждого нарушения на CWE / БДУ ФСТЭК (с прямой ссылкой на bdu.fstec.ru) / ГОСТ-clause.

**Подтверждение концепции на коде Сбера.** В апреле–мае 2026 нами выполнен **публичный double-audit** на трёх флагманских открытых Python-репозиториях `ai-forever` (Sber AI): `giga_agent` (LangGraph-агент), `gpt2giga` (FastAPI-прокси OpenAI → GigaChat), `gigachat` (Python SDK). Корпус 622 файла, ≈ 65 000 LOC; **449 нарушений до фикса, 422 после; 80 % находок — P8 (sequential await + `async_def_no_await`)** — прямой риск SLA для async-инфраструктуры. На `giga_agent` отдельно зафиксированы **45 случаев `unbounded_orm_all`** (P9.2) — каждый такой `.all()` без `.limit()` это потенциальная DoS / OOM-уязвимость под нагрузкой. Полный отчёт — `docs/SBER-TBANK-DOGFOOD-REPORT.md`.

**Eat-our-own-dogfood: density 0 на собственном production-коде.** В мае 2026 проведён self-audit ПОЛИНОМа на собственной кодовой базе (64 файла, 14 616 LOC):

| Tree | Files | LOC | Density |
|---|---:|---:|---:|
| детекторы (libcst-визиторы) | 33 | 4 617 | **0.0000** |
| трансформеры (auto-fix) | 14 | 1 056 | **0.0000** |
| CLI / pipeline / shared | 6 | 3 556 | **0.0000** |
| web-playground/backend | 11 | 5 387 | **0.0000** |

False-positive формы (FastAPI handlers, daemon-loops, sequential retry, module-level regex compile) помечены `# sigma:allow` с обоснованием в коде. Подробный отчёт — `docs/DOGFOOD-V0.5.2-SELF.md`.

Это **proof-point**, на который мы готовы публично опираться: продукт прошёл собственную методологию.

**Подтверждение академической стороной.** Черновик нормативного документа P-Safe-профиля, подготовленный независимым аналитиком на базе тех же статей (IEEE 2024 + Mathematics 2024 Q1), прошёл peer-review проектной команды POLINOM. Принят концептуальный сдвиг: **«POLINOM не подменяет академическую методологию, а индустриализирует её»**. Аналитик принял четыре поправки к черновику (отказ от runtime-обёртки `fcall/freturn`, отказ от тотального запрета `while`, от запрета goroutine, от трактовки P-Safe как закрытого DSL); три конструктивных элемента (Псевдо-EBNF профиля, нормативный режим `PASS / FAIL / WARN`, Java-аннотация `@PRecursive(decreases=...)`) приняты в дорожную карту v0.5 и в техническое задание Java Phase 1. Полный текст — `docs/REVIEW-RESPONSE-PSAFE-DRAFT.md`.

## Проблема, которую решает продукт

Производственные Java-микросервисы СберТеха содержат миллионы строк кода. Существующие инструменты качества покрывают:
- **Линтинг и code smells** — SonarQube, Coverity, Checkstyle.
- **Уязвимости и зависимости** — Snyk, OWASP Dependency-Check.
- **AI-помощь при написании** — GigaCode (контекстная подсказка, completion, review-комментарии).

Что не покрывается ни одним из перечисленных классов: формально-доказуемая принадлежность кода к классу полиномиально-вычислимых функций. В коде остаются паттерны, которые проявляются только под нагрузкой — sequential await вместо параллельного `gather`, рекурсия без контракта убывания, ORM-запросы без `.limit()`, `def`-объявления внутри циклов. Каждый из этих паттернов — потенциальный SLA-инцидент в продакшене.

Цена одного SLA-инцидента в платёжной инфраструктуре банка: десятки часов on-call времени, downtime регулируемых сервисов, регуляторные риски по 683-П и ГОСТ Р 57580.1-2017. По нашим эмпирическим данным на 5 контрольных корпусах (7 100 файлов, ~840 K LOC), от 30 до 80 % нарушений в любом достаточно большом Python-проекте относятся именно к этому методологическому классу.

ПОЛИНОМ закрывает этот разрыв в специализированной нише. На Java его действие предполагается аналогичным — Phase 1 как раз и содержит эмпирическую валидацию методологии на JVM, привязку к закрытому Java-стеку Сбера и подготовку технического задания для построения `sigma-audit-java`.

## Финансовые условия

### Этап 1 — НИР: Python production audit + Java baseline + ТЗ Java-CLI

**Срок:** июнь — ноябрь 2026 (6 месяцев)
**Запрашиваемое финансирование:** **25 000 000 рублей** (в рамках действующего соглашения о партнёрстве)
**Результат:**

1. **Python — закрытый аудит на стеке Сбера.** Прогон `sigma-audit` на 10–20 закрытых Python-репозиториях по выбору заказчика (CodeOwner-команды Sber AI, СберДевайсы, инфраструктурные сервисы). Локально, под NDA, ничего не покидает периметра. Результат — единый HTML-отчёт по каждому репозиторию + сводный документ с приоритизацией по бизнес-риску.
2. **Java baseline — эмпирическая валидация методологии на JVM.** Расширение существующего бенч-стенда `bench-java` (Apple M2 / OpenJDK 19 / JMH 1.37) до 25–30 контролируемых случаев из закрытой Java-кодовой базы СберТеха. Цель — определить, какие правила методологии переносятся на JVM дословно, какие требуют адаптации, какие инвертируются.
3. **Техническое задание Java-CLI.** Документ ТЗ по ГОСТ 19.201-78 на построение `sigma-audit-java` v0.1 — детекторы, AST-форма (через `JavaParser` или `Spoon`), формат интеграции с GigaCode и GitVerse, API-аннотации `@PRecursive(decreases=...)`, `@PSafeLoop`, `@PSafeCall`.
4. **Отчёт о НИР** в формате ГОСТ 7.32-2017, переданный в ЦИИ НГУ как соавтору методологии и заказчику первой волны.

### Этап 2 — ОКР: Java-CLI v1.0 + интеграция в GigaCode и GitVerse

**Срок:** декабрь 2026 — июнь 2027 (7 месяцев)
**Запрашиваемое финансирование:** **30 000 000 рублей**
**Результат:**

1. **`sigma-audit-java` v1.0** — Java/Kotlin CLI с 18+ детекторами (Java-проекция Python-набора v0.4 плюс Java-специфика по итогам Phase 1), 8+ авто-трансформерами с verify, sandbox-режимом, ГОСТ-19 документацией.
2. **Адаптер к GigaCode** — расширение AI-ассистента специализированными правилами Сигмы, которые не покрывает обобщённая LLM-проверка. Передача правил методологии в формате MCP-совместимого rules pack.
3. **Интеграция в GitVerse** — `sigma-audit` как **partner technology** в подсистеме статического анализа GitVerse: badge `P-SAFE PASS / WARN / FAIL` в UI кода, возможность включить как обязательный gate в merge request.
4. **Эмпирическая валидация** — пилотный прогон на 3–5 production Java-сервисах СберТеха с измеримой метрикой density (нарушений на файл) до и после внедрения.

**Совокупно Этапы 1+2+3 — 115 000 000 рублей на 19 месяцев.**

## Экономика для Сбера

**Прямой ROI года 1.** Сокращение SLA-инцидентов класса «sequential await под нагрузкой» (75 % находок на нашем эмпирическом замере на МТС-корпусе, 80 % на Сбер AI giga_agent) на 30–50 % в течение года. При средней стоимости одного критического инцидента в платёжной инфраструктуре банка (десятки часов on-call, downtime, регуляторное обоснование) **окупаемость Этапа 1 (25 М ₽) достигается уже после 2–3 предотвращённых инцидентов** на любом достаточно крупном production-сервисе.

**Усиление GigaCode.** На независимом замере на репозитории `mts-ai/FastAPI-JSONAPI` агент с правилами Сигмы (наш агентский pack) нашёл **в 2.3 раза больше методологически релевантных нарушений**, чем CLI-инструмент сравнимого класса. Адаптация этих правил в GigaCode (Этап 2) даёт измеримый прирост качества AI-ассистента в специализированной нише.

**Регуляторный контур.** В свете требований 683-П, ГОСТ Р 57580.1-2017 и приказов ФСТЭК к категориям К1–К3, наличие сертифицированного методологического анализатора с доказательной базой (ГОСТ-19 пакет, ссылки на IEEE 2024, эмпирическая валидация на 7 100 файлах) — это **снижение регуляторного риска**, не только техническое улучшение.

**Сравнение с альтернативной разработкой.** Самостоятельная разработка аналогичного инструмента с теоретической базой потребовала бы привлечения профильных специалистов по теории вычислимости, JIT-инфраструктуре и методам формальной верификации — оценочно 150–300 М ₽ и 18–24 месяца, не считая риска отрицательного академического результата. ПОЛИНОМ — готовая теоретическая база (опубликованная и рецензируемая) + production-готовый Python-инструмент. Phase 1 работает на закрытие Java-периметра поверх уже сделанной работы.

**Дополнительный эффект, не отражённый в прямом ROI:** появление в банке собственного методологического стандарта качества кода с привязкой к научной школе СО РАН. Это и репутационный аргумент для аудиторов (ЦБ РФ, ФСТЭК), и конкурентное отличие при найме разработчиков высокого уровня.

## Конкурентная позиция

Ни один из коммерческих SAST-инструментов на российском или международном рынке не реализует методологию формальной верификации полиномиальной сложности с привязкой к конкретной академической школе. Coverity и SonarQube — общеотраслевые линтеры, не методологические анализаторы. GigaCode — AI-ассистент, не статический верификатор. Coverity Enterprise (Synopsys) для команды 50+ разработчиков стоит от 50 тыс. долл. в год; SonarQube Enterprise — от 30 тыс. долл. — оба инструмента **дополняют**, а не заменяют ПОЛИНОМ.

**Запас по времени.** Самостоятельная разработка академически обоснованного методологического анализатора крупным банком или вендором — оценочно 18–24 месяца с риском отрицательного результата. Текущая стартовая точка ПОЛИНОМа — 22 готовых детектора Python, 5 контрольных эмпирических замеров (7 100 файлов / 840 K LOC), полная ГОСТ-19 документация, peer-review с академической стороной. Это даёт **запас 12–18 месяцев** до того, как любой потенциальный аналог достигнет сравнимой готовности.

Свириденко (соавторы методологии). Инженерная команда POLINOM реализует продуктовый и инструментальный слой; академическая сторона обеспечивает теоретическую корректность и продолжение публикационной активности.

## Следующий шаг

Предлагаем провести **техническую демонстрацию работающего инструмента** в одном из двух форматов:

**Формат А — публичный web-playground.** Открываем https://polinom-sigma-audit.up.railway.app в браузере на демо-встрече, вводим URL одного из открытых Sber AI-репозиториев (`ai-forever/giga_agent`, `gpt2giga`, `gigachat`) — через 30 секунд показываем интерактивный HTML-отчёт с density-метрикой, привязкой каждого нарушения к CWE / БДУ ФСТЭК / ГОСТ, каскадным разворотом скрытых паттернов. Никаких слайдов, никакой инсталляции. **Это самый сильный demo-формат** — компиляция презентации и продукта в одном экране.

**Формат Б — закрытый аудит на стеке Сбера.** На случай, если выбранные репозитории — приватные:

- *Локальная инсталляция CLI под NDA* — `pip install sigma-audit` на машине Сбера, ничего не покидает периметр, результат — те же HTML-отчёты.
- *Публичная папка Яндекс.Диска с privacy-mode* — загрузить zip-архив выбранного приватного репо на disk.yandex.ru/d/... → кинуть ссылку в web-playground → получить отчёт за 30 секунд → удалить с диска. **Источник нигде у нас не сохраняется** (audit_cache, permalink_cache, supply-chain БД — все обходят Я.Диск-источники). Это самый быстрый способ получить отчёт по приватному коду без устанавки CLI.

Демонстрация занимает **30 минут**, на выход — единый HTML-отчёт `audit → fix → audit` с конкретными файлами, строками, классификацией нарушений по 32 правилам в 7 семействах и merge-инструкциями.

После демонстрации — **2 рабочие недели** на согласование ТЗ Этапа 1 в рамках действующего соглашения о партнёрстве. Содержательное наполнение НИР Phase 1 готово к подписанию.
